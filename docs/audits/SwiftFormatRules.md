# SwiftFormat rule coverage

This audit maps SwiftFormat's rules to the Bylaws correction APIs.

## Scope

The inventory uses [SwiftFormat 0.64.1](https://github.com/nicklockwood/SwiftFormat/releases/tag/0.64.1),
released on 22 October 2026, at commit
[`f53853b330ff`](https://github.com/nicklockwood/SwiftFormat/commit/f53853b330ff8dc61f92d489df57bf5c33491c5b). The audit date is 23 October 2026.
The [rule catalogue](https://github.com/nicklockwood/SwiftFormat/blob/f53853b330ff8dc61f92d489df57bf5c33491c5b/Rules.md) and
[generated registry](https://github.com/nicklockwood/SwiftFormat/blob/f53853b330ff8dc61f92d489df57bf5c33491c5b/Sources/RuleRegistry.generated.swift)
contain the same **169 rule IDs**: 117 default, 44 opt-in and 8 deprecated.
Every ID has one row below. The source declaration's default/deprecated state
was checked against the catalogue, and every registered ID has a source file.

The comparison uses Bylaws commit `c2583513b7a07e202508d0709a6d57f442883ec8`,
which contains the source layout API. This source review maps authoring routes.
A matching route establishes neither an implemented rule nor option parity.
The table records the route before the audit and after its general API improvements.
The final column describes the remaining rule logic.

## How to read the table

- **Direct**: the main policy fits existing model, whitespace or layout APIs.
  The author supplies selection and ordering logic. Boundary restrictions can
  stop a correction, so this does not claim complete upstream behaviour.
- **Source edit**: existing source projections support a text replacement,
  insertion or removal. The author assembles the replacement and checks context.
- **Native syntax**: the available models do not describe enough structure for
  a general implementation to be clear. A Swift Testing rule can inspect
  SwiftSyntax through `SourceFile.withSyntax` and make exact source edits.
  A narrow portable variant can be easier.

Before the improvements, the counts were 19 direct, 27 source edit and
123 native syntax. The current routes are 22 direct, 99 source edit and
48 native syntax. Each count includes deprecated aliases.
None of the rows claims full rule or option parity. SwiftFormat's rules all
propose source changes, so this catalogue has no diagnostic-only rules.
The native syntax route can reproduce its local syntactic checks. A stronger
semantic guarantee can need compiler data that neither a syntax tree nor the
layout builder supplies.

**Family tested** refers to an existing Bylaws test of a related operation.
It does not mean the SwiftFormat rule has been ported. **Reviewed** means the
route is based on source inspection without a matching end-to-end rule test.
Each rule name links to the pinned upstream implementation.

## API evidence

The original layout replacement takes a nonempty collection from one source snapshot.
It supports attributes, modifiers, members, statements, call arguments,
parameters, enum case elements and array/dictionary elements. Attribute,
modifier and comma-separated lists must be complete. Members and statements
can be a consecutive region. The layout emits every original element once,
retains its text and preserves the existing trailing-comma policy.
See [the replacement contract](../../Sources/BylawsSemantics/Model/Source/SourceLayoutReplacement.swift)
and [the supported syntax lists](../../Sources/BylawsSemantics/Model/Source/SourceLayoutReplacement+Syntax.swift).

An [Import](../../Sources/BylawsSemantics/Model/Declarations/Import.swift)
has its module path, kind, attributes, visibility and captured source. Ordinary
import grouping can use these models. A grouping rule must preserve conditional
scope and comment ownership.
[SourceNode lists](../../Sources/BylawsSemantics/Model/Syntax/SourceNode+Lists.swift)
expose members, statements, modifiers, parameters, case elements and attributes.
[SourceSpacing](../../Sources/BylawsSemantics/Model/Source/SourceSpacing.swift)
exposes adjacent whitespace.

[SourceSlice](../../Sources/BylawsSemantics/Model/Source/SourceSlice.swift)
provides whole-file access, checked UTF-8 subranges, regex matches and exact
replacements. Native rules can inspect the full tree through
[SourceFile.withSyntax](../../Sources/BylawsSemantics/Model/Source/SourceFile+Syntax.swift).
This escape hatch makes many rules feasible, but it does not make their
context checks or range selection easy.

The existing tests cover
[attribute ordering, member groups, statement spacing and nested argument layout](../../Tests/CoreTests/Corrections/LayoutRuleTests.swift),
[modifiers, parameters, enum elements and comment attachment](../../Tests/SemanticsTests/Model/Source/SourceLayoutReplacementTests.swift)
and [integer-literal corrections](../../Tests/InterpreterTests/Runtime/CorrectionRuleTests.swift).
They also cover Unicode character widths, tabs, LF/CRLF/CR endings and
multiline-string indentation limits. They do not test all SwiftFormat rules.

The follow-up APIs expose [typed tokens](../../Sources/BylawsSemantics/Model/Source/SourceToken.swift)
and [comment/whitespace trivia](../../Sources/BylawsSemantics/Model/Source/SourceTrivia.swift)
through every source provider. Token neighbours keep original-file context, and
file trivia includes comments at EOF. These projections remove manual range
selection from many lexical rules. The rule still chooses the context and policy.
[Composed edits](../../Sources/BylawsSemantics/Model/Source/SourceSlice+Corrections.swift)
combine non-overlapping edits within one captured source region.

The expanded list projection uses `SourceNode.elements` for conditions, generics,
inheritance, expressions, tuple types/patterns, closure parameters/captures and
switch cases/items. The layout preserves their list inventory and separators.
These additions support more ordering and wrapping policies without custom
SwiftSyntax rewriters. A structural migration can still take substantial logic.

## General API changes and remaining work

1. The changes add source-backed tokens and trivia with typed lexical kinds,
   exact source,
   neighbouring tokens and adjacent whitespace. This gives spacing, braces,
   semicolons, comments and literal rules an alternative to whole-file regex or
   custom SwiftSyntax range calculations. String and regex contents must keep
   their lexical identity.
2. The changes add source-backed projections for more syntax lists:
   conditions, generic parameters/arguments/requirements, inherited types,
   tuple/closure elements and switch patterns. Protocol composition continues
   to use token edits. Shared separator and ownership checks apply to the lists.
3. The changes compose non-overlapping edits within one captured source region.
   This lets a containing layout element include several inner corrections.
   Snapshot and conflict checks remain in place. Source insertion/removal still
   uses checked slices and replacement text.
4. The changes expose comment trivia. Attachment policy remains rule logic.
   A rule must choose
   whether documentation moves with a declaration, comments stay in a region or
   formatting directives stop a correction. Comments should not be found through
   unrestricted text matching.

These improvements reduce source-location work. They do not implement a Swift
name resolver, effect checker, macro expander or deployment-availability model.
For example, removing `async`, narrowing visibility, replacing `count` with
`isEmpty` or deleting an unused declaration can depend on information outside
one syntax tree. A rule can reproduce SwiftFormat's local heuristics or use
available compiler-index queries, with that choice stated in its own policy.

The full `wrapArguments` rule includes generics, conditions, aliases, effects
and result types. A successful argument-list example establishes only part of
that rule. Likewise, `wrapEnumCases` splits one comma-separated declaration
into several declarations, and `sortSwitchCases` sorts patterns within a case
label. Existing enum/member ordering tests do not establish those behaviours.

## Verification limits

No upstream conformance suite ran against Bylaws. To claim parity for a rule,
port its relevant positive, negative and option cases and run the rule through
both `Bylaws.swift` and Swift Testing where supported. Include comment ownership,
conditional compilation, interpolation, Unicode, language-version constraints
and unchanged second-run output.

The correction engine checks snapshots, overlaps and parse errors. It does not
prove that a corrected program type-checks or keeps its behaviour. The layout
also stops at unsupported comments, directives, conditional boundaries and
semicolon-separated forms. An unsupported boundary should remain an explicit
limit instead of a silent text-edit fallback.
