# SwiftLint rule coverage

This audit maps every rule in SwiftLint 0.65.1 to the current Bylaws correction APIs. It compares the layout-only baseline with the token, trivia and syntax-list APIs in this change. Each route identifies the work left to the rule author.

## Scope and evidence

The audit uses [SwiftLint 0.65.1](https://github.com/realm/SwiftLint/releases/tag/0.65.1), released on 21 August 2026 and checked against the official latest-release API on 23 October 2026. The pinned source commit is `6aba03e3d8302b33f106e0f922210f35ca4b52cf`.

The [built-in registry](https://github.com/realm/SwiftLint/blob/6aba03e3d8302b33f106e0f922210f35ca4b52cf/Source/SwiftLintBuiltInRules/Models/BuiltInRules.swift) lists 254 rules. The [core registry](https://github.com/realm/SwiftLint/blob/6aba03e3d8302b33f106e0f922210f35ca4b52cf/Source/SwiftLintFramework/Rules/CoreRules.swift) adds `custom_rules` and `superfluous_disable_command`. All 256 canonical identifiers occur below once. Five deprecated aliases are listed separately. The inventory checks the registered types against their primary `RuleDescription` metadata, rather than counting every Swift file or every example. `statement_position` has two descriptions with the same identifier and counts once.

The Bylaws baseline is `c2583513b7a07e202508d0709a6d57f442883ec8`. The current routes include captured tokens, captured trivia, composed source edits and the 16 additional syntax-list kinds in this change. A changed route records a source-based feasibility judgement. It does not establish upstream equivalence.

There are 103 default rules, 148 opt-in rules and five analyser rules. The source declarations identify 92 rules with correction support. The Default, Opt-in and Analyser labels describe SwiftLint registration. The correction column describes SwiftLint, rather than a Bylaws implementation.

This is a source-based feasibility audit. It does not establish equivalent behaviour for every configuration, syntax form or upstream example. No SwiftLint rule has a complete equivalence test in Bylaws as part of this audit. Existing Bylaws tests cover narrower examples of attribute ordering, property grouping, statement spacing, nested argument layouts and correction validation. Those tests are evidence for those examples, not for SwiftLint parity.

## How to read the routes

| Route | Meaning |
| --- | --- |
| Direct | The captured models and layout builder express the main policy without a custom SwiftSyntax visitor. The rule author supplies selection and conditions. The layout safety limits remain. |
| Source edit | Captured source slices and text replacement express the main policy. Regex, input selection and replacement logic remain author code. |
| Native syntax | Exact token, trivia, expression or scope information takes SwiftSyntax work. Native Swift Testing can host that code, and the CLI can collect its corrections. The layout builder does not make that work easy. |
| Semantic | Equivalent behaviour takes compiler information or whole-program assumptions beyond the available source projections. Existing Bylaws index queries answer some related questions but do not supply all SwiftLint analyser responses. |
| Diagnostic only | Bylaws can report the condition through a suitable model or native syntax check. An automatic correction takes a project decision, external information or an operation outside the correction API. This does not forbid a project from defining a narrower fix. |
| Unsupported | The rule depends on SwiftLint execution state that Bylaws does not reproduce. A related comment check is possible, but it would have different behaviour. |

A Direct route is not a claim that all upstream cases fit. Layouts reject ambiguous comment ownership, unsupported semicolons and conditional-compilation boundaries. They preserve each captured list element exactly once. They cannot add or remove an element, change punctuation policy or determine that a reorder preserves program behaviour. Captured tokens and trivia identify editable content and whitespace without translating SwiftSyntax offsets. Source replacements can change that content, while the author supplies the matching and replacement policy.

Portable `Bylaws.swift` supports the documented interpreter subset. Native syntax work generally belongs in a compiled Swift Testing rule. Both surfaces can return corrections to the same CLI run. See [Formatting source](../../Sources/Bylaws/Bylaws.docc/FormattingSource.md), [Correcting source](../../Sources/Bylaws/Bylaws.docc/CorrectingSource.md) and the [portable API table](../../Sources/Bylaws/Bylaws.docc/RunningRulesFromTheCLI.md#supported-api).

## General API coverage and remaining gaps

Captured `tokens` and `trivia` close the source-targeting gap for literal, punctuation, comment and adjacent-whitespace edits. Tokens retain their lexical kinds, source slices, neighbours and trivia. A rule can propose edits without calculating a UTF-8 range from a diagnostic.

The additional `elements` projections cover condition lists, generic parameters and arguments, generic requirements, inherited types, labelled expressions, tuple type and pattern elements, closure parameters and captures, enum associated-value parameters, primary associated types, accessors and switch lists. Complete-list layout checks retain punctuation and source ownership. They can refuse a comment or conditional boundary instead of guessing how to move it.

These APIs remove mechanical source lookup. They do not classify every declaration or establish the meaning of an expression. Token-level spacing must distinguish the grammar context where a policy differs. For example, a colon can belong to a type annotation, a dictionary element or a ternary expression. A switch list supplies cases, but there is no dedicated projection for a case label's final colon and its first statement.

Structured expression projections remain useful for call-chain rewrites, operator comparisons and closure-to-key-path rules. The API must expose operand identity and precedence. A text match against a receiver name cannot establish that a call uses the standard library implementation.

Binding-aware local scope queries would help unused parameters, redundant `self` and variable shadowing. A local analysis must state which scopes and syntax it covers. It cannot promise type-checked reference resolution.

Insertion and deletion remain source replacements with an author-defined policy. The layout builder preserves every selected element once. It cannot turn an inventory-preserving reorder into a safe member removal, symbol rename or control-flow rewrite.

The correction and formatting cookbooks exercise narrower token, trivia, list and composition examples. The per-rule rows remain feasibility judgements. They do not claim that the upstream rule's full examples and options pass.

## Compiler-analysis limits

SwiftLint's five analyser rules are distinct from its ordinary syntax rules. Their source implementations use compiler arguments, SourceKit cursor responses, referenced symbol identities or module-usage data. In particular:

- `typesafe_array_init` checks the resolved `map` overload and its generic type.
- `explicit_self` checks whether a reference is an instance member.
- `capture_variable` resolves capture identities and whether the declarations are mutable.
- `unused_declaration` gathers declarations and references across the files being analysed.
- `unused_import` uses module-usage information, including missing explicit imports.

Bylaws' index data is tied to selected targets and a build configuration. It cannot prove the absence of callers in other packages or runtime entry points. Public index occurrence APIs do not expose all SourceKit cursor and module-usage responses. A fresh index prevents stale-source decisions, but it does not add that missing information. A rule must state its supported build scope and choose a conservative failure policy.

## What remains to verify

Equivalent rules need tests against the pinned upstream examples and the relevant configuration choices. Tests must cover unchanged input, corrected output and a second run that proposes no further edits. Comment attachment, conditional compilation, macros, Unicode, line endings, multiline strings and interacting corrections need separate cases where the rule can affect them.

The inventory is complete for this release. The implementations and their equivalence tests remain work to do. The Direct and Source edit rows identify the most useful starting points. Native syntax and Semantic rows identify the capabilities to design before claiming that those rules are easy to write.
